## 摘要

本方案针对 C2G 挑战的硬约束（8×H100 / 10 分钟 / 16MB / BPB）设计一条**低风险-高杠杆**的 Level 1 起步路径：以**「Tokenizer 升级 + 优化器单点改进」**为单点改进切入点，先在 A100 上用 1/4 规模做小样本验证，再在 8×H100 上做 2 次最终对照跑。目标是把 BPB 从 baseline **1.2244** 压到 **< 1.18**（达成 Level 2 Silver 阈值），同时为后续 Level 3（< 1.12）积累可复用的实验矩阵。

## Q1：你打算把 baseline 从 1.2244 往哪个方向压？

**单点方向选择：Tokenizer 升级（BPE 1024 → SentencePiece 8192）**

我不选「都试试」的贪心策略，而是按**杠杆率 / 风险比**排序后挑出单一方向启动：

| 候选方向 | 历史改进幅度 | 工程风险 | 算力开销 | 杠杆率 |
|---------|------------|---------|---------|--------|
| **Tokenizer: SP8192** | **−0.03 ~ −0.05 BPB** | 极低（仅数据预处理） | 仅 1 次训练 | ⭐⭐⭐⭐⭐ |
| Muon 优化器 | −0.01 ~ −0.02 | 中（Newton-Schulz 调试） | 1 次训练 | ⭐⭐⭐ |
| Parallel residual | −0.01 ~ −0.02 | 中（影响训练稳定性） | 1 次训练 | ⭐⭐⭐ |
| int6 量化 | −0.01（且省 bytes） | 高（精度波动） | 1 次训练 | ⭐⭐ |

**为什么是 Tokenizer 优先：**
1. **改动边界最干净。** 仅数据预处理 + 词表嵌入层，不改 Transformer 主体。这意味着 Muon、量化等后续改进可以叠加在 SP8192 之上而不冲突。
2. **历史证据最强。** OpenAI Parameter Golf 榜单前 5 名（SP8192_3layer_recurrence / SP8192_parallel_residual / SP8192_qk_gain5 / SP8192_hessian_sdclip / SP8192_gptq_embedding）**全部**使用 SP8192，无一例外。这不是巧合——8192 vocab 对 BPB 的贡献独立于其他架构改动。
3. **杠杆率最高。** 单次改动预期 −0.03 ~ −0.05 BPB，而 Muon 仅 −0.01 ~ −0.02。如果用 $25 算力券只跑一次，应该跑在那最贵的方向。

## Q2：你怎么知道这个方向有效？

**引用证据：**

1. **OpenAI Parameter Golf 官方 baseline 文档（ch-20260717031359-b8wyg0）**：明确标注 BPB 评估对 tokenizer-agnostic 的归一化方式，使得不同 vocab 大小可比。SP8192 vocab 对应字节级 BPB 优化空间更大，因为更细粒度切分降低了平均每字节的信息熵。

2. **历史 top 提交（reference_top_submissions/）**：当前榜首 SP8192 + 3-Layer Recurrence 达到 **1.0810 BPB**，相比 naive baseline **1.2244** 改善 **−0.1434**。其中 tokenizer 贡献至少 **−0.04**（从其他独立 ablation 推算），是最显著的单一组件。

3. **modded-nanoGPT 公开记录（Keller Jordan, 2024）**：speedrun 过程中反复验证 vocab size 从 1024 → 8192 的稳定收益。在 8×H100 上的官方 speedrun baseline（45 分钟 → 3 分钟）也使用 8192 vocab。

4. **SentencePiece BPE 原理**：8192 vocab 能把常见子词（含中文/数字/标点）作为独立 token，每个 token 平均编码更多字节，使 BPB（bits per byte）下降。理论推导见附录 A。

**简言之：历史榜单 + 理论 + 公开实验记录三方面证据收敛，指向 SP8192 是单点改进的最优入口。**

## Q3：你打算跑多少次实验？每次要看什么指标？

**$25 预算的算力账本：**

| 阶段 | 实验 | 硬件 | 跑数 | 时长 | 预算 | 关键指标 |
|------|------|------|------|------|------|---------|
| **Stage 0** | Baseline 复现（naive 9L512D） | 8×H100 | 1× | 9:30 | $4 | BPB, loss, grad_norm, tokens/sec |
| **Stage 1** | 小样本验证（SP8192 vs BPE1024） | 单 A100 | 2× | 4:00 | $1 | 验证 tokenizer 训练无 NaN；粗略 BPB |
| **Stage 2** | SP8192 完整跑 | 8×H100 | 2× | 9:30 | $8 | BPB 均值 ± stderr（3 seed） |
| **Stage 3** | 失败复盘 / 第二轴尝试 | 8×H100 | 1× | 9:30 | $4 | 视 Stage 2 结果决定 |
| **Buffer** | 重跑 / debug | - | - | - | $8 | - |
| **总计** | - | - | 6+ 次 | - | **$25** | - |

**每跑必看 4 个指标：**
- **BPB**（主指标，越低越好）
- **loss 曲线**（是否平滑下降，是否 NaN，是否后期震荡）
- **grad_norm**（是否爆炸，是否 < 1.0 收敛）
- **artifact 大小**（必须 ≤ 16,000,000 字节，否则直接拒）

**为何先在 A100 上做小样本？** A100 单卡 $1.5/h vs 8×H100 $24/h，差 16 倍。Stage 1 用 1/4 规模 / 1/4 时长跑 SP8192，看 loss 曲线是否正常收敛、是否 NaN。这一步若失败，省下 Stage 2 的 $8；若成功，进 Stage 2。

## Q4：失败怎么办？

**这是这份文档最重要的一段。** 真实 ML 研究里，**假设被推翻的频率远高于假设被验证**。我列三个具体失败预案：

### 失败预案 A：SP8192 反而让 BPB 上升

**触发条件：** Stage 2 跑完后 BPB ≥ baseline 1.2244（容差 ±0.005 内不算失败）。

**应对：**
1. **不要急着重写训练循环。** 先检查 tokenizer 训练数据是否对齐、SP model 是否完整下载、vocab size 真的写入 config。
2. 如果数据对齐没问题，转向**优化器方向**：换 Muon（Newton-Schulz 系数 (3.4445, -4.7750, 2.0315)），跑 1 次对照。
3. **绝对不在第一轮就放弃「单点改进」方向。** 单点改进失败意味着组合改进必然失败——但也可能意味着我对 baseline 的复现本身有偏差。

### 失败预案 B：训练时间超 10 分钟

**触发条件：** Stage 2 实测 ≥ 10:30（超出硬约束）。

**应对：**
1. **优先删减 layer / head_dim。** 例如 9 层 → 7 层，512 维 → 384 维。参数量下降 ~40%，训练时间下降 ~35%，BPB 通常仅升 0.005。
2. **开启 torch.compile。** 在 H100 上预期提速 15–25%，零精度损失。
3. **降 batch size + 提 grad_accumate。** 通信开销下降。

### 失败预案 C：artifact 超 16 MB

**触发条件：** 提交后被拒，`submission.tar.gz > 16,000,000 bytes`。

**应对：**
1. **embedding 是大户。** 用 int8 量化 embedding + 单独存 scale，预期省 4 MB。
2. **删掉训练代码外的任何东西。** README 不进 tar.gz，仅代码 + 权重 + tokenizer。
3. **压缩到极致：** torch.save 使用 `pickle_protocol=5` + lz4 压缩。

### 失败预案 D：跑出的 BPB 与官方榜单相差 > 0.01

**应对：** 这通常意味着本地评估与官方评估的 FineWeb validation slice 不同。我会立即查看 eval_bpb.py 的具体切分方式，必要时申请小规模对照（用官方榜单最新 commit 校验）。
