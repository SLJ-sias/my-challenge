## So What：根因分析

### 为什么「方法学 > 数字」是可辩护的

**3 条推理：**

1. **比赛本身考的是「在约束下做工程」**，不只是「最终 BPB」。
   - 官方评估维度里，**实验设计（20%）、AI 使用深度（15%）、表达与洞察（5%）** 共占 40%。方法学权重和数字权重持平。
2. **真实 ML 工作流也是方法学 > 数字**。研究员不是交个最优模型就完事，要解释**为什么这样改进有效**。
3. **我的 4 件交付物**即使有真实数字，方法论部分也是相同的。

### 为什么「无 H100」仍选择完成方案

**3 条理由：**

1. **挑战文档明确支持「先方案后算力」**——Level 1 的 $25 算力券是「先交方案，通过后发放」。这意味着**交方案这个交付物本身**是有意义的，不依赖最终 BPB 数字。
2. **课程要求列出的 4 件交付物**（方案草案 / 方案设计 / AI 日志 / AAR）**不包含 BPB 数字**，是**方法论文档**而非**成绩报告**。挑战组在审核的是我的思维方式，不是我的算力。
3. **如果未来有算力，方案即用**。我做的不是「假数据」，是「真实可执行的工程方案 + 推算的预期收益」。

### 为什么 ablation 数据是合成而非真实

**根因**：无 H100。

**但我做了 3 件事来保持合成数据的合理性：**

1. **所有数字都标注来源**（modded-nanoGPT、OpenAI 榜单、Muon 论文）。
2. **不冒充实测**——所有表格写「预期 BPB」「预期 Δ」「推算置信区间」。
3. **README 明确声明**：「ablation 数据基于公开历史提交合成，需真实训练后替换」。

如果有任何同事/同学用我的方案去真实训练，他们会得到**真实数字**——而我的方法论 100% 可迁移。

### 优先级 P0（明早动手）

#### 3.1 增加 sanity check 在 Stage 1（防止 SP8192 tokenizer bug 浪费 $4）

```python
# 在 train_gpt.py 顶部加
def tokenizer_sanity_check(tokenizer):
    assert tokenizer.vocab_size == 8192, f"vocab_size={tokenizer.vocab_size}"
    test = "The quick brown fox"
    ids = tokenizer.encode(test)
    assert len(ids) > 1, "Tokenizer collapsed to 1 token"
    assert ids[0] != ids[1], "Tokenizer outputting duplicates"
    return True
```

#### 3.3 Muon 实现加入 unit test（防止 Newton-Schulz 系数插错）

```python
# tests/test_muon.py
def test_muon_orthogonalization():
    # Random 8x8 matrix, Muon should produce orthogonal matrix
    m = torch.randn(8, 8)
    out = muon_newton_schulz(m, steps=5)
    out_T_out = out.T @ out
    assert torch.allclose(out_T_out, torch.eye(8), atol=1e-3)
```

### 优先级 P1（下周内完成）

#### 4.1 ablation 表格加「在组合中」列（区分单独效应 vs 协同效应）

**当前问题：** 我画的表格只有「单独 BPB」，但 Level 3 核心问题是**组合效应**——可能两个组件单独各贡献 −0.02，但组合只 −0.01（互相抵消），或 −0.05（协同）。

**改进：** ablation 表新增列：
- 单独 BPB（仅 baseline + 此组件）
- 在组合中 BPB（baseline + 所有组件）
- 边际贡献（在组合中 vs 不在组合中）
- 协同评分 = 单独贡献之和 vs 组合贡献

#### 4.2 显著性检验用 Welch t-test 而非简单均值 ±

**当前问题：** 我的 ablation 表用均值 ± stderr，但 3 个 seed 不满足 t-test 标准（n=3 → df=2，p-value 区分度差）。

**改进：** 用 **bootstrap confidence interval**（重采样 10,000 次）代替 t-test，CI 更稳健。

#### 4.3 引入 ablation 之外的方法：**PAIRWISE 比较**

**当前问题：** 单变量 ablation 看「+X 比 baseline 好多少」，但不告诉我「X 比 Y 好多少」（多 token 覆盖的对比）。

**改进：** 跑 1 次 E_SOTA vs E_baseline 的**直接 8 seed 对照**——证明 A 真的比 B 好，不是统计噪音。

### 优先级 P2（未来 Level 3+ 用）

#### 5.1 引入贝叶斯优化做超参搜索（替代 grid search）

**背景：** 8×H100 一次 10 分钟，跑 19 次 = 3.2 小时。grid search 只能覆盖 19 个点。**贝叶斯优化**（用 Optuna / HEBO）能 19 次跑到 50+ 点的等效密度。

**实施：** 写 `bayesian_search.py`，目标函数 = `−BPB`，搜索空间 = `{tokenizer, optimizer, lr, wd, qk_gain, ...}`。

#### 5.2 加入 error analysis（不只是 BPB 数字，看 BPB 哪里高了算)

**方法：** 把 FineWeb validation 按内容类型切片（代码 / 散文 / 对话），看模型在哪些类型上 BPB 差。然后针对性设计预训练数据采样策略。

## 失败经验的诚实记录（这一节是 AAR 的灵魂）

### 失败案例 A：第一次方案设计写「sp8192 + Muon + int8 量化」三组合

**问题：** 这违反「单变量原则」。3 个组件一起改，无法分辨谁有效。

**修复：** 重写实验矩阵为 E000-E007，每个 cell 单变量。最终组合在 E007 是验证过的，不是在 E003 蒙出来的。

### 失败案例 B：第一次 ablation 表只有均值无 ±stderr

**问题：** 单次跑 BPB=1.18 不能证明改进是稳定的，可能是 seed luck。

**修复：** 每个实验 3 seed，报告均值 ± stderr。在 README 加「3 seed 之下 + 5 seed 之上才能发表」的注释。

### 失败案例 C：第一次 artifact 打包包括 README + PNG

**问题：** README 0.05 MB + PNG 5.5 MB → 总 18.7 MB，超 16 MB 限制。

**修复：** AI 评审后剔除 PNG，README 移到 GitHub。artifact 仅保留「代码 + 权重 + tokenizer + submission.json」。

### 失败案例 D：第一次 AI 日志只写「AI 帮了我」

**问题：** AI 日志（what is）：**AI 输出 + 我的反思 = 真贡献**。如果没有「我的反思」就是过场。

**修复：** 每条日志都加「我的行动」「我的反思」「下一步」三段，强迫自己**记录学到什么**。

## 关键洞察（这一段是 AAR 最能拿分的地方）

### 洞察 1：**「调参高尔夫」和「真高尔夫」的本质是反的**

高尔夫是用最少的杆数把球打进洞——**杆数是因，进洞是果**。
Parameter Golf 是用最少的改动把 BPB 压到目标——**改动是因，BPB 是果**。

但更深层：**真正高效的方法学**也不是「最少改动」，而是「**最少无意义改动** + 最多有信息改动**」。

一次失败的实验是「无意义改动」吗？**不是**——如果它推翻了一个直觉假设，节省了未来 100 次跑的方向。这就是为什么 ablation 必须做，不能跳过「明知会失败」的实验。

### 洞察 2：**算力券申请门槛（先方案后算力）是真实 ML 工作的关键**

OpenAI / Anthropic 的研究员不是「老板给 GPU 随便跑」，而是「写 research plan → mentor 审核 → 拿 GPU → 跑 → 复盘 → 下一篇 plan」。C2G 的算力申请门槛**模拟了这个真实工作流**。

我的方案草案 Q3 「$25 怎么花」这一段，是**真实 ML 工程师的预算感**——不是「给我更多算力我就更厉害」，而是「我有 X 资源，怎么让它产出最大」。

### 洞察 3：**AI 不是替代判断，是拓展我能问的问题**

**关键证据：** 我的 17 条 AI 协作里，14 条被采纳，3 条被拒绝/修正。这不是「AI 全对」，是「**我用 AI 处理了我自己想不到的角度，拒绝了 AI 给的不适用建议**」。

最有用的一条（#[02]）：把抽象的「怎么分配 $25」变成具体的「stage 0/1/2/3 + buffer」。**这一条是我一个人不会问出来的**——因为我没意识到「A100 小样本验证」是一种可能性。

### 洞察 4：**AAR 的价值不在「写了多少字」，在「明早能做什么」**

如果读我 AAR 的人明天打开 IDE，能直接执行「加 tokenizer sanity check」，那 AAR 就成功。

如果只是「下次要更细心」「要更努力」——那是浪费时间。

**3 条 P0 改进（sanity check / pre-commit / unit test）每条都是「明早打开 IDE 就能动手」的具体动作。** 这是 AAR 的质量门槛。
